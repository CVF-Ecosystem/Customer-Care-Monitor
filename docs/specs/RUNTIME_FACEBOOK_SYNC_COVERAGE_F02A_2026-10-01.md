# CCMAI-RUNTIME-022 / F02-A — Facebook sync window coverage

Status: SPEC accepted for bounded WORK_ORDER. Date: 2026-10-01. Risk: R2 (channel data and sync checkpoint). Authority: [F01–F08 source review](../reviews/CCMAI_F01_F08_LOCAL_SOURCE_REVIEW_2026-09-30.md), [runtime roadmap](../roadmaps/AI_RUNTIME_GATES_AND_EVIDENCE_2026-09-27.md), existing R013–R016 sync admission/ownership behavior.

## Observed source and scope decision

`SyncReservedChannel` passes `limit=100` to every adapter (`backend/engine/sync.go:390`). `FacebookAdapter.FetchRecentConversations` breaks at the limit even when `paging.next` remains (`backend/channels/facebook.go:70-142`). A run can then report success and advance `last_sync_at` to its finish time, leaving unvisited eligible conversations older than the next run's one-hour overlap. The Facebook adapter also returns early on the first item older than `since` based on an ordering assumption that this code does not verify. On a later page error, it returns a partial slice **with an error**; the engine currently records error and does not advance the success checkpoint.

The same shared 100 limit may truncate Pancake and Zalo. R022 repairs **Facebook only** so the source change and evidence stay bounded. F02 remains OPEN for a separate audit/repair of Pancake and Zalo before any claim of complete cross-channel sync coverage. No real Facebook incident or live API behavior is asserted by the source finding.

## Intended contract

1. For a Facebook channel, the engine requests exhaustive conversation coverage for the selected `since` window; non-Facebook calls retain their current limit and behavior under R022. The adapter must follow every valid `paging.next` until a terminal page, examining all returned rows. It includes conversations with `updated_time >= since` (inclusive boundary), skips older rows, and does not stop on the first older row unless ordering is independently guaranteed by a separate accepted contract. No hidden 100-row success limit remains.
2. Exhaustive success means a terminal page was observed and every eligible row from every visited page was considered. Missing/malformed `data`, missing/invalid conversation ID or timestamp, invalid/unsafe/cyclic pagination URL, context cancellation, page/read/decode/API error, or a safety budget reached before terminal is **incomplete coverage** and returns an error. A partial slice may be returned with the error for diagnostics, but the engine must not process it as a successful complete window or advance `last_sync_at`. Safety bounds must fail closed; they must not silently truncate or produce `success`.
3. Validate `paging.next` before following it: HTTPS and the expected Graph host/path family only; reject cross-host and non-HTTPS URLs. Do not log or return an access token, raw paging URL or response body on pagination or network error. Preserve the existing credential mechanism and message fetch behavior, except for a narrow shared request-error sanitization needed to prevent token-bearing URL leakage.
4. Keep tenant/channel/run-ID ownership, lease heartbeat, R013 single-flight, R014/R015 side-effect fencing, R016 lease behavior, per-conversation partial status, and the existing one-hour overlap. `last_sync_at` advances only after complete Facebook enumeration and all selected conversation/message work succeeds. Page errors and budget errors record a bounded non-success status; after-sync jobs do not fire. Retry with the same prior success checkpoint can fetch and upsert the full window without duplicate rows. No persistent cursor/schema migration is introduced in R022.

## Acceptance evidence

- Local synthetic Graph-page tests (no Facebook call) cover 250+ eligible conversations over at least three pages, an older row interleaved before a newer eligible row, equality at `since`, and a terminal page. Show all eligible unique IDs are returned exactly once; test a cap/limit request that would truncate and require an error instead of a misleading success. Verify the failing behavior against pre-BUILD source through a reversible probe or recorded mutation.
- Page cases: an empty page with a valid `paging.next` must continue and can succeed after a terminal page; a terminal empty page is allowed. Page two API/read/decode failure, malformed `data`/ID/time, repeated cursor, unsafe host/scheme, cancellation and safety budget each return an error. No secret-bearing URL/token appears in response/log. Tests must demonstrate a positive path for the same page transport/observer.
- Disposable-MySQL engine test with a recording adapter proves Facebook receives exhaustive mode and can ingest >100 eligible conversations across a window. A failed second page (or equivalent adapter error after partial data) leaves `last_sync_at` at the previous success value, records non-success and does not fire after-sync jobs; a retry completes without duplicate conversation/message rows and then advances the checkpoint. Non-Facebook limit 100 stays unchanged. The test must observe stored rows/checkpoint, not only mock call counts.
- Run focused channel/engine tests, relevant existing R013–R016 sync regressions, full backend suite on disposable MySQL, R019 five-sentinel gate on the full JSON log, `go build ./...`, downstream preflight, catalog, doctor and diff check. Record commands, exit codes, cleanup and limits. Synthetic adapters/Graph pages prove application sync semantics only, not live channel delivery or CVF AI governance.

## Decision boundary

No changes to Pancake/Zalo, adapter interface, DB schema, API/UI, provider routing, real Facebook channel, persistent Compose data, deployment, push or FREEZE. If exhaustive Facebook paging cannot be completed under a bounded resource budget, the run reports incomplete coverage and keeps the prior success checkpoint; a resumable cursor is a separate tranche. F02 is not fully closed by R022.
