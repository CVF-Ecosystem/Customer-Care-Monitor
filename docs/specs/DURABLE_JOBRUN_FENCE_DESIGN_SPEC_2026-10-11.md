## Current source facts that constrain the design

HTTP trigger and test-run, MCP dispatch, cron, after-sync, agent analysis, and direct Analyzer entry points converge on the reservation and shared execution path. Test-run is a mode on that path, not a separate ownership mechanism. Current admission uses a process-local owner map, locks the Job row, counts matching JobRun rows whose status is running, and inserts a running row. The local owner and cancellation token are not persisted. The scheduler source has no JobRun startup sweep; that source fact says nothing about binaries or other writers not represented by this comparison. [S01][S04][S05][S06][S07][S08][S11][S12][S13][S14]

Current Job and JobRun models have no persisted incarnation/generation grant. Result persistence checks inserts in a transaction, but its current parent locks are Conversation then JobRun; it does not prove the active owner. Admission, destructive guards, and finalization use Job then JobRun. The normal finalizer stores run status and Job status/checkpoint with readback; its best-effort error fallback is weaker. The coordinator registry mutex protects the local owner map and is released before admission or cancellation DB reads; `GuardJobMutation` does briefly query that map while holding the Job row lock. Separately, `JobRunOwner.publish` holds the per-owner mutex through its result transaction, which is how accepted local cancellation is serialized against publication. Cancellation completes its checked row read before taking that owner mutex; terminal code takes and releases the owner mutex before its DB finalizer. These facts do not fence a second process. [S08][S09][S10][S15]

The current effect paths include provider calls, usage rows, snapshots/evaluations/results, initial and progress summaries, terminal/checkpoint writes, activity, notification sends/logs/markers, and worker release. The notification dispatcher sends after terminalization, writes NotificationLog and notified_at without checking those DB errors, then returns. The current result-clearing, channel deletion/purge, demo reset, and CLI prune paths have distinct locking or timing behavior; they are mapped below rather than inferred safe from the owner guard. [S03][S09][S10][S16][S17][S18][S19][S20][S21]

## Design decision and alternatives

**Selected intended direction — DB-owned monotonic generation plus an active grant on the Job row.** The protected data and admission state already live in the project database, and the source uses Job/JobRun row transactions. A generation stored and checked in that same database can be bound to every protected database transaction. An external token allocator would still need every database writer to check its token in the transaction that commits the data; a lease by itself cannot reject stale DB writes. The DB-owned option adds no independent coordinator dependency and gives a concrete same-database predicate. Its safety depends on complete writer adoption and old-writer compatibility, neither of which is current evidence. [S06][S08][S09][S15][S22]

| Option | What it can enforce | Availability and adoption consequence |
|---|---|---|
| DB-owned monotonic generation with active grant — selected | Admission and DB writers can atomically compare the current Job grant with the immutable JobRun tuple while holding the Job row lock through commit. | Adds a short Job-row serialization point and schema work. Any writer that omits the predicate bypasses it. Old binaries must be stopped or proven compatible before deployed reliance. |
| External fencing-token allocator | Can allocate a token only if the token is then stored and checked by every database writer in its commit transaction. | Adds coordinator availability, partial-failure, and rollout dependencies without removing the DB enforcement work. It cannot fence a provider or notification call already sent. Not selected. |
| Keep unresolved runs blocking | Existing compatible source keeps a matching running row busy. In the selected design, an observed active grant, mismatched tuple, or unfenced running row blocks; an ambiguous caller result is resolved from a fresh locked row observation, not by assuming the grant persisted. | Can leave a Job unavailable indefinitely. This is a fail-closed source-compatible fallback, not a guarantee about unknown, older, mixed, or external writers. No age, TTL, local-map absence, or process restart reclaims a grant. [D01][D02][D04][D05] |

The selected direction is an intended database contract, not a claim that a generation field alone is sufficient. A writer that does not lock and verify the exact active tuple is outside the fence until adopted or quiesced. A generation cannot undo a remote effect or establish that an external request failed without effect. [S09][S17][D02]

## Intended persisted identity and state

The logical ownership tuple is **T = (tenant_id, job_id, run_id, generation)**. The Job UUID is the incarnation boundary: every create or recreate path must mint a fresh server-side UUID and must not accept or recycle a caller-supplied old Job ID. If any future import or administrative path can reuse a Job ID, this tuple is insufficient and a durable non-reused incarnation value must be added before implementation. The current HTTP create path generates a UUID server-side; it is not proof that all possible writers do so. [S02][S15]

The intended data shape, not present in source, is:

| Record | Intended fields and invariant |
|---|---|
| Job | `fence_generation` is an unsigned monotonic counter; `active_run_id` and `active_run_generation` are either both null or both set. The counter is never decremented or reset while this Job UUID exists. Counter exhaustion fails admission closed; it never wraps. |
| JobRun | Persist `fence_generation` captured at admission. Existing tenant, job, and run IDs plus that generation must exactly match the Job's active grant before a protected write. A run's captured generation is immutable. |
| Active grant | The pair `(active_run_id, active_run_generation)` identifies the one admitted run for that Job. The grant remains present across terminal status and the post-terminal tail. It is cleared only by an exact, checked retirement transaction after all synchronous worker effects and durable markers have settled. |

Pre-fence rows need an explicit cutover rule in the migration plan. Do not infer an owner or clear a running row during migration: any legacy running row blocks cutover and requires separate recovery authority. Legacy terminal rows are not proof that an old notification/effect tail has stopped; the old-writer drain/cutover barrier must precede reliance on the new grant protocol. The documentary gate below must specify the reserved legacy generation/backfill choice and how a failed cutover leaves jobs unavailable. No startup sweep or automatic retirement is proposed. [S08][S15][S22]

Job ID is not a tenant-global counter. It is the non-reused incarnation UUID. A newly created Job receives a fresh identity; a stale writer holding the deleted Job ID cannot match a different Job. A different rule is required if an out-of-band path can restore or reuse an ID. This is an implementation-readiness condition, not an assumption about deployment. [S02][S15]

The intended persisted states are derived from the exact grant and run row, not from age or process presence:

| Persisted observation | Intended decision |
|---|---|
| No active grant and no running JobRun, with the old-writer cutover barrier satisfied and no unresolved legacy tail | Eligible for a distinct explicit admission after exact locked read and checked transaction. |
| Active grant exactly matches one running JobRun | That tuple alone may perform ordinary run writes and terminalize. A second admission is busy. |
| Active grant matches a terminal JobRun | Terminal tail only: completion/activity records, notification attempts/logs/markers, then exact retirement. All analysis, usage, result, summary, checkpoint, and provider-start effects are closed. Another admission remains busy. |
| Active grant missing or mismatched; duplicate/missing run; or run is running without a grant | Reject/no-op. Do not repair the row, clear a different grant, infer owner death, or retry a possibly committed transition. Reconciliation/recovery is a separate authority. |
| Terminal JobRun with no active grant | May accept a new explicit admission only after the old writer paths are on the compatible fence or quiesced. The row state is not evidence of deployed compatibility. |

An ambiguous response is a caller-local observation, not a persisted state or proof of commit/rollback. Its safe next step depends on the transaction phase:

| Ambiguous transaction | Required next observation and allowed consequence |
|---|---|
| Admission | The caller never dispatches and never clears or automatically retries the reservation. A later coordinator takes the same authoritative Job row lock. If it sees the exact active tuple, it rejects as busy; if atomic rollback left no grant and no running row, it may admit a new explicit request with the next generation. If it cannot obtain that locked observation, it admits nothing. |
| Protected writer or terminal transition | The transaction does not retire the grant. The caller stops later effects and does not repeat a write or transition based on an uncertain result. The active grant continues to block admission; exact readback may classify the persisted run state but does not itself authorize replay. |
| Retirement | Retirement is attempted only after terminal-tail work and old synchronous DB writers are drained. A later coordinator takes the same Job row lock: an active grant is busy; a terminal row with no grant may accept a new explicit admission. An unavailable or mismatched read fails closed. The prior caller never resumes the tail or retries a possibly completed remote effect. |

These outcomes depend on one transactional authoritative database and the Job row lock serializing admission, protected writes, terminalization, retirement, and destructive paths. Source configuration identifies MySQL/GORM, but actual engine/version, isolation, commit/readback behavior, and implicit locks are not established here; the bounded next documentary gate and later isolated tests must verify the applicable fixture. No caller stopping is represented as a persisted global hold. [S06][S08][S22]

## Admission, write guard, terminal tail, and retirement

**Admission.** Create the run ID before the transaction. Lock the tenant row first, then the exact tenant-scoped Job row, then matching JobRuns in stable ID order. This short Tenant lock serializes admission with tenant-wide channel/reset operations and Job create/config updates; it intentionally serializes admissions within one tenant for the brief reservation transaction. The transaction checks that the active-grant pair is empty, checks for any incompatible running row, verifies counter capacity, increments the counter, creates exactly one JobRun with the captured generation, sets the active-grant pair, and verifies the exact persisted tuple before commit. A statement failure before commit rolls back; a commit or readback error leaves the outcome unknown and does not imply rollback. Dispatch starts only when the admission transaction itself returns committed success. If that caller receives an ambiguous commit/readback result, it never dispatches, uses later readback to resume the reservation, clears, or automatically retries. A different explicit request must acquire the Job lock and sees either the committed active tuple (busy) or the atomic rollback state (no grant/no running row, subject to the cutover/legacy-tail barrier). A failed or unavailable locked observation admits nothing. The local owner map remains a cancellation aid only; the registry mutex is released before a database wait. [S06][S08]

**Protected DB writes.** Every transaction that mutates data for a run begins at the Job lock, then locks the exact JobRun, then (when conversation-bound) locks Conversation rows in ascending stable ID order, then writes child rows. It verifies tenant, Job UUID, run ID, generation, active-grant pair, and allowed run state in that same transaction. It holds these locks until commit. Missing/wrong/terminal identity is a checked no-op/rejection with no writes. A pre-transaction read is advisory and cannot authorize the later write. A statement/commit/readback uncertainty stops later effects and forbids an automatic repeat; this transaction never clears the active grant, so any subsequent admission still sees it as busy. No blanket all-writer claim is made until every source path adopts the predicate. [S06][S08][S09][S10]

**Terminal transition.** The finalizer locks Job then JobRun and requires the exact current grant and a running row. It writes the JobRun terminal state and Job status/checkpoint together and verifies both. The grant is deliberately retained. Ordinary clean completion alone may advance the ordinary checkpoint; test-run and other explicit modes, errors, partial work, and cancellation do not gain checkpoint advancement. If terminal commit/readback is uncertain, do not run the notification tail, release, or automatically repeat finalization; the retained grant blocks a new admission while the caller resolves or fails closed. The current source's `terminalFailed` reopens local cancellation after a write error; the future implementation must distinguish a known rollback with exact running-row readback from an ambiguous result and keep the owner non-publishable while outcome remains unknown. A best-effort status update that cannot verify the exact tuple never clears the grant. [S08][S10][D02]

**Post-terminal tail and retirement.** After verified terminalization, only exact-run activity/notification work is allowed. Before each tail DB write, the writer verifies the same tuple and terminal state. The future notification path must check and durably record every configured destination's attempt result, check NotificationLog writes and notified_at updates, and distinguish known send failure from an unknown send outcome. A known, durably logged failure is not replayed. If send outcome, log commit, marker commit, or readback is ambiguous, do not resend or infer no delivery; keep the active grant and do not attempt retirement until the tail's durable state is known. Retirement is one final transaction that locks Job then JobRun, verifies the exact tuple, terminal state, and completed durable tail markers, and clears only the active-grant pair. Generation remains unchanged. It runs only after all synchronous calls and spawned work have returned or been joined. The Job lock serializes retirement with every guarded writer: an earlier writer finishes before retirement, and a later writer sees no matching grant. If retirement's response is lost, a new admission uses a fresh locked observation: the still-active grant is busy; a retired terminal row may admit a distinct generation. The old owner issues no further DB writes or tail effects in either case. A terminal status by itself never proves the old effect path has stopped. [S07][S08][S09][S16][S17]

The DB fence applies only to DB writers that participate in it. Provider and notifier calls get an exact-tuple check immediately before dispatch, but that check cannot be held atomically with the remote service. Once a request is sent, an error or lost response does not prove whether the remote effect occurred. The worker must not retry a possibly sent request as part of fencing, and the design makes no remote exactly-once, retroactive cancellation, or replay-safety claim. Retirement waits for the local synchronous call path to return and its DB markers to be known; it cannot prove when an external service completes its own effect. [S09][S16][S17]

## Mutation, deletion, and lock-order contract

The intended database lock partial order is **Tenant → Job → JobRun → Conversation → child rows**. Admission, Job create/config update, channel/purge, reset, and multi-Job prune acquire Tenant first. A single-Job writer or mutation may begin at Job; a run writer then takes JobRun and, when conversation-bound, sorted Conversation rows. Operations may begin at a suffix only if they never acquire an earlier class later in the transaction. All multirow locks use stable ascending IDs within each class.

The local synchronization contract is separate from that DB order. `coord.mu` protects only the owner-map registry. Current reserve inserts and unlocks before DB admission; cancel looks up and unlocks before its checked DB read; release removes the owner after worker effects. `GuardJobMutation` currently holds the Job row lock while briefly querying the map (`Job → coord.mu`), but no current registry holder waits for a DB lock. Future code must preserve that no-`coord.mu`-across-DB-wait rule and must not introduce a reverse registry-to-DB edge. The per-owner `o.mu` is different: `publish` intentionally holds it through the result DB transaction so cancellation waits for that commit or publication never begins. Cancel completes its DB read before requesting `o.mu`; terminal decision locks `o.mu` and releases it before finalizer DB locks. Future code may preserve the `o.mu → DB` publication edge but must never call `o.mu` while holding a DB row/transaction lock. Do not nest `coord.mu` with `o.mu`; preserve the brief current `Job → coord.mu` lookup without adding a path that waits for DB while holding `coord.mu`.

The `o.mu` winner rule is: cancellation acquired before `publish` suppresses that publication; publication acquired first holds through commit and cancellation may be accepted afterward. Before terminalization, an accepted local cancel closes cancelled and cannot advance the ordinary checkpoint. `beginTerminal` acquired first refuses later cancellation and owns the terminal outcome; reopen cancellation only after a known rollback plus exact readback of the still-running tuple. An unknown terminal outcome stays non-publishable and does not accept a later cancel. This preserves local ordering only; it adds no cross-process cancellation. This is the target logical graph; actual MySQL/GORM row and implicit foreign-key locks, isolation, query plans, and commit/readback behavior still require the bounded documentary gate and later isolated-database tests. [S06][S08][S09][S19][S20][S21][S22]

| Existing path | Current interaction | Required future integration |
|---|---|---|
| UpdateJob / CreateJob | CreateJob mints a server UUID; UpdateJob applies an allowlist directly and does not take the run guard. [S02] | Internal fence fields are never client-writable. Create/recreate must mint a fresh Job UUID. Both operations lock Tenant first; UpdateJob then locks Job and rejects every update while any grant is active, including terminal tail. |
| GuardJobMutation / DeleteJob / ClearJobRuns | GuardJobMutation locks Job and checks local ownership plus running rows; DeleteJob and ClearJobRuns then lock runs and delete/reset data in transactions. [S03][S08] | Guard must reject any active grant, including terminal-tail grants, not only running status/local owner. Lock Job then JobRuns in stable order and check every child statement. Busy rejects before mutation. A known statement rollback is distinct from an ambiguous commit; after uncertainty, report unknown and do not claim rollback or retry. |
| ClearJobResults | Current path plucks run IDs and performs multiple unchecked, nontransactional deletes without GuardJobMutation. [S03] | Convert to one checked transaction; lock Job then sorted JobRuns, reject any active grant, delete results/snapshots/usage/notification rows, and return no success on statement/commit error. A known statement rollback is distinct from an ambiguous commit; do not retry or claim no deletion after an unknown result. |
| DeleteChannel / PurgeChannelConversations | Current code locks Conversation rows then deletes result/snapshot/message children and channel state; file removal follows commit. It does not acquire Job/JobRun. [S19] | For this tenant-wide destructive operation, lock Tenant then all tenant Jobs and JobRuns in stable order, reject if any active grant exists, then lock affected Conversations and delete children. Do not acquire Job or JobRun after Conversation. This broad gate can block unrelated jobs, an explicit availability cost. File removal follows only confirmed DB commit; on ambiguous commit leave files untouched and do not report rollback. No JobRun token can roll back filesystem effects. |
| ResetDemoData | Current path locks Conversations then JobRuns, opposite the selected writer prefix, and deletes Jobs, runs, results, messages, and other tenant rows. [S20] | Reorder to Tenant → all Jobs → all JobRuns → all Conversations in stable order; block the reset if any active grant exists. Tenant-scoped creation/admission/configuration paths must participate in the Tenant prefix so reset cannot race a new Job/grant. A known statement error rolls back; an ambiguous commit may have committed atomically, so the caller must not claim rollback or retry. A later reset/admission observes the current locked state. |
| CLI prune | Current CLI counts running runs once before planning/apply; later batch transactions delete results/snapshots without rechecking grants. [S21][S23] | Treat the initial count as advisory only. Re-read each batch under locks in Tenant/Job/JobRun/Conversation order, sort targets, and reject the batch on any active grant or changed plan. On ambiguous batch commit, do not repeat that batch; a later plan starts from locked persisted state. Include this operational writer in adoption before any fleet claim. |
| All other database writers and old binaries | The inspected repository sources are not a census of deployed processes, external SQL, or older binaries. [D05][D06] | Inventory and adopt every writer before relying on the fence. A writer that cannot be upgraded must be stopped/quiesced and evidenced before rollout reliance. No present all-writer or fleet guarantee. |

This lock contract specifies the logical order and the intended changes to the named paths. It does not claim that the existing DB schema, GORM-generated statements, implicit foreign-key locks, or unknown deployed MySQL isolation already satisfy it. If a future DB test finds an inverse/hidden lock edge or any delete can commit around a guarded writer, stop implementation, return to DESIGN, and amend the graph before release. Do not weaken the active-grant check to make a test pass. [S19][S20][S21][S22]

## Readiness limits, roles, and next governed move

The contract selects an architecture and specifies the named repository integrations; it is not implementation-ready. The next bounded documentary gate must bind the logical transaction outcomes and local-mutex edges above to the versioned MySQL/GORM schema, exact row-lock/query shapes, FK and multirow lock interactions, Tenant-prefix participants, and all Job ID create/recreate paths. If those facts cannot be resolved from source, the gate remains open rather than reading a live DB/host or assuming a deployment. After that gate, isolated tests must validate the target fixture and every mapped writer, including ClearJobResults, channel/demo deletion, and prune. A separately authorized adoption packet must upgrade or quiesce old binaries and out-of-repository writers before deployed reliance. Unknown topology alone did not prevent design selection; it prevents any fleet claim. [S02][S19][S20][S21][S22][D05][D06]

The paired work-order draft is proposal only: its immediate candidate move is a bounded documentary lock/outcome gate with zero tests/runtime/DB activity; the later R2+ implementation outline remains non-executable and requires a new immutable seed and independent reviewer.
