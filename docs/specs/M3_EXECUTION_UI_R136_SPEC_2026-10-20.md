## Intended API contract

Add two bounded **GET** routes under the existing tenant/case/request path. Neither GET starts a job, issues/reserves/consumes a grant, debits budget, calls a provider, rewrites request status, or invokes the claim function. Both return `Cache-Control: no-store`; avoid provider/model, config reference, issuer/evidence reference, key, prompt, manifest, budget amount and raw error text in responses.

1. `GET /api/v1/tenants/:tenantId/intervention-cases/:caseId/rerun-requests/:requestId/execution-readiness` requires known tenant membership plus `intervention_cases:r,w` and `jobs:w`, the same route-level writer permissions as execute. Re-read tenant/case/request/revision/job/channel, current case version, no active execution, current local source digest/coverage, process synthetic capability, an issued actor-bound grant with `deadline > serverNow`, and available job budget. An uncertain DB/source read returns **503** `{error:"readiness_unavailable"}` with `Cache-Control: no-store`, no handle or invented state. On positive observation return **200** `{state:"READY",request_id,expected_case_version,server_now,expires_at,grant_handle}` with all fields present and a positive integer version; `expires_at` is the observed grant deadline. On a known unmet prerequisite return **200** `{state,request_id,server_now}` with `state` one of `AWAITING_OPERATOR_AUTHORITY`, `PROCESS_DISABLED`, `STALE_OR_INELIGIBLE`, `ALREADY_STARTED`; omit `grant_handle`, `expires_at` and `expected_case_version`. `grant_handle` is the existing grant ID treated as an opaque client-internal handle and appears **only** for `READY` to the matching actor. It is not displayed, logged in ordinary UI, stored persistently or accepted from user text. A missing grant does not disclose another actor's grant. The GET result cannot guarantee a later POST; locked POST admission rechecks everything, including the later budget check.
2. `GET /api/v1/tenants/:tenantId/intervention-cases/:caseId/rerun-requests/:requestId/execution-status` requires `intervention_cases:r`, current tenant membership and scoped case/request ownership. It reads the original request and its unique execution row by `(tenant_id, request_id)` without requiring configured transport or `jobs:w`. On a successful read return **200** `{request_id,request_intent,execution_present,phase,observed_at,terminal_code?,published_case_version?,proposal_available?}`; `request_intent` is the unchanged stored request status (`AWAITING_EXECUTION_AUTHORITY` for the current path). `phase` maps the durable row to `NOT_STARTED`, `CLAIMED`, `CALL_MAY_HAVE_STARTED`, `RESPONSE_RECORDED`, `PUBLISHED`, or `MANUAL_HOLD`; terminal codes may identify `DENIED`, `STALE_SOURCE`, `OUTPUT_INVALID`, `PROVIDER_UNKNOWN`, `SETTLEMENT_FAILED`, `CANCELLED`, `RECOVERY_REQUIRED` through safe localized UI wording. `published_case_version` and `proposal_available` appear only after verifying the execution's **linked published run/proposal/event lineage**; never copy a later mutable current case version into this historical result. On a failed read return **503** `{error:"status_unavailable"}` with no guessed no-row/terminal phase. The original request intent remains unchanged. `PUBLISHED` is linked by request → execution → new run/proposal and the refreshed same-case detail; do not infer publication from an HTTP 202, a stale proposal, or the request's `NOT_RUN`. `execution_present:false` says only “no committed execution row observed at this read,” never “no call happened” after an uncertain POST.

For both GETs, 401 means unauthenticated; 403 means membership/permission denied; 404 means tenant-scoped case or request absent; 503 means status/readiness cannot be established. Readiness may return 200 with a non-ready state for an observed business prerequisite; 400 is reserved for malformed input. Execute POST keeps its existing 400/403/404/409/503 behavior and 202/200 shape. The frontend displays understandable Vietnamese/English messages, not raw enum, grant ID, provider/config data, stack text or raw backend error. Avoid turning a status GET into a permission side channel: reader can see execution history, but only eligible writer can discover a grant handle.

## User and uncertainty contract

On every case-detail load, including `OPEN` after publication, show the saved request separately from its latest observed execution status. The follow-up capture/request form may remain WAITING_ON_DATA-only; place request-linked execution history/status in a parent or sibling detail component that survives the state transition. A reader sees the safe history and no execute control. A user without `jobs:w`, revoked `intervention_cases:w`, wrong tenant, stale actor grant, missing budget/config, expired/consumed grant, changed source or case version sees an explanation and no enabled control. An unavailable/unknown readiness also disables it. Show `READY` only from a fresh read for the current tenant/case/request/actor/session/permissions, with server-supplied deadline; the server clock decides expiry. Before each deliberate click, refresh detail and readiness, show a concise execution consequence and ask for one explicit action. Immediately **before dispatching the POST**, synchronously persist an `IN_FLIGHT` marker in origin-scoped local storage, keyed to tenant/case/request/actor identity and containing only marker state/time, then lock duplicate submission; if storage is unavailable or the write fails, do not send. At the click, send exactly the two POST fields from that fresh readiness. No automatic execute, retry, resend or token-refresh replay.

Treat 202 as admitted, not complete. Read the status GET and same-case detail to show progress/result; bound observation to at most twelve status reads, at least five seconds apart, over at most one minute, then offer manual refresh. Cancel reads and ignore late responses when tenant, case, request, token, actor, role or permissions change, or on unmount. Reload may resume read-only observation. The pre-send `IN_FLIGHT` hold survives browser crash/reload before any response handler runs; transition it to uncertain on timeout, abort, connection loss, 5xx or unknown POST completion, and retain it across logout/session reset with no grant/body/credential content, displaying it only after the same actor reauthenticates. After a known 202, keep read-only observation rather than permitting another action. Do not release the hold solely because a temporary status GET sees no row or still sees an issued grant: admission may be in flight. A confirmed durable execution may transition to observed progress or terminal result. Otherwise keep the action disabled for explicit operator reconciliation under separate authority. A different device may lack the local marker; server-side uniqueness/locked admission remains the final one-call fence. A 409, stale detail, revoked permission or changed session forces a fresh read and no repeat POST. Preserve the exact attempted body identity only in protected diagnostics if needed for independent investigation; client error text cannot prove success, no-call or refund.

Grant issuance remains an operational prerequisite under separate server authority. An operator must deliberately provision synthetic startup and a current budget/grant for the intended actor/request. This design does not activate an installed system, expose grant issuance or provider settings, add recovery/retry/bulk behavior, or claim that R117's consumed provider slot is reusable.
