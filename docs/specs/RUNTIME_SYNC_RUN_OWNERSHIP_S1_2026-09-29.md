# S1 sync run identity and final-write ownership

**Tranche:** `CCMAI-RUNTIME-014` · **Phase:** SPEC · **Risk:** R2 · **Entry:** R001–R013 independent REVIEW PASS / FREEZE open; S1 IN_PROGRESS.

## Source finding and decision

R013 uses a conditional `last_sync_status='syncing'` reservation. It has no identity for the admitted run. If a later recovery clears a stale `syncing` row while an older worker is still alive, the older worker can finish after a new run has set the row back to `syncing`; its final write can then overwrite the new run. The manual panic write has the same gap. `Channel` has no run/lease field, `AutoMigrate` runs before scheduler startup, and existing `syncing` rows cannot be attributed to a process. This tranche establishes identity for new reservations and fences **final status/checkpoint writes**. It does not reclaim stuck rows or assert fencing of conversation/message/provider side effects.

## Contract

1. Add a nullable, internal `sync_run_id` to the channel model/schema. Do not serialize it in channel APIs or backfill legacy rows. A successful shared reservation atomically sets `syncing`, clears the prior error and assigns a new unpredictable run ID in the same conditional update. Return a typed reservation containing tenant, channel and run ID only on exactly one affected row. Busy, missing/changed tenant and DB failure remain bounded and never dispatch work. Two accepted generations for one channel must have distinct IDs.
2. Carry the reservation through manual launch/worker/panic recovery and through `SyncEngine.SyncChannel`/`SyncReservedChannel`. The already-reserved entry must verify that its passed reservation matches its channel before adapter work. Do not infer ownership from the channel snapshot or a global variable. Preserve manual 202/409/404/500 shapes, validated config before reservation, scheduler busy skip and agent non-success behavior from R013.
3. Every final success/partial/error and deferred error transition, including manual panic recovery, must require `(id, tenant_id, last_sync_status='syncing', sync_run_id=that run ID)` and exactly one affected row. A successful terminal transition clears the ID in the same write. A stale worker with an old ID may report an ownership-lost error but cannot advance `last_sync_at`, replace the new run's status/error, or trigger after-sync jobs. A failed terminal write does not claim completion; an error transition may be attempted under the same ID only. Logs/responses must not reveal token, SQL detail or credentials.
4. Fresh-schema and pre-existing-schema migrations must be idempotent. Existing `syncing` rows with NULL `sync_run_id` remain blocked and unchanged; this tranche does not silently adopt or clear them. Existing idle rows can receive a new run ID on their next admitted sync. No scheduler startup sweep, timeout reclaim, lease expiration, background heartbeat, new endpoint, provider call or persistent Compose DB mutation is authorized.
5. This is **final-write fencing only**. The sync engine currently performs conversation/message upserts, attachment work and token-refresh persistence during a run. If a future recovery can release a channel while an old worker is alive, those side effects need an additional ownership/cancellation design before enabling automatic reclaim. A later recovery tranche must define evidence of worker death or safe side-effect fencing, including multi-process and mixed-version behavior. Do not label R014 as crash recovery or full run fencing.

## Acceptance

- Disposable MySQL: fresh and old schema migration, second migration, NULL legacy `syncing` row retained, idle row admission, same-channel concurrent one-winner result, tenant isolation, DB error/zero-row admission. Assert the assigned ID is internal and never sent in channel JSON or error/log text.
- Accepted synthetic run: manual, scheduler and agent paths carry the same ID from reservation into the worker; R013 202/409 and busy no-work behavior remains. Success/partial/error final writes clear only the owning ID; only success advances checkpoint and triggers after-sync work.
- Controlled two-generation race: reserve A, simulate a recovery-like status release only inside the fixture, reserve B, then let A finish/fail/panic. A must not modify B's status, error, checkpoint or ID; B can complete. A wrong-tenant, missing, NULL-ID or forged-ID final write must affect zero rows. Detect regression to status-only predicate and to worker dropping the ID.
- Focused and full backend tests on disposable MySQL, `go build ./...`, `go vet ./...`, catalog `-Check`, project doctor and diff check. Record migration/rollback and mixed-version limits. Synthetic tests do not prove live channel behavior or CVF governance.
