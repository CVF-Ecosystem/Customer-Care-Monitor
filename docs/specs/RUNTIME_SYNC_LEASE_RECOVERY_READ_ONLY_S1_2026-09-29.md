# S1 conditional recovery of expired read-only channel sync runs

**Tranche:** `CCMAI-RUNTIME-016` · **Phase:** SPEC · **Risk:** R2 · **Entry:** R015 independent `REVIEW_PASS`, FREEZE open; S1 IN_PROGRESS.

## INTAKE and DESIGN decision

R013 blocks a second sync while a channel remains `syncing`. R014 gives each accepted run an ID; R015 fences local persisted effects after that ID loses ownership. A crash after reservation can therefore leave the channel blocked indefinitely. The current `facebook` and `pancake` sync adapters issue GET requests; Zalo can issue a single-use token refresh POST. An expired timestamp does not prove that a process died or that an outbound request ended.

R016 permits **conditional release of an expired run only for the explicit GET-only `facebook` and `pancake` allowlist**. It relies on R015's ownership fence for local writes and unique attachment keys. A former worker may finish an in-flight GET, but must not publish data or advance the checkpoint after release. `zalo_oa`, unknown types, rows from pre-R016 binaries, and legacy `syncing` rows without a run ID remain blocked. No provider call already in flight is claimed to be canceled or undone. A later tranche must decide Zalo and legacy recovery with stronger process-death or provider-boundary evidence.

## Contract

1. Add an internal nullable lease deadline to `channels` through the ordinary idempotent migration. Admission remains one atomic tenant/channel/busy-checked reservation. For a new allowlisted run, store its run ID, `syncing` status and a future lease deadline in the same accepted write, using the database clock. For every other type, store NULL. No old row is backfilled. A non-NULL deadline is the R016 protocol marker, so a mixed older binary cannot silently make its own run reclaimable.
2. While an allowlisted run is active, extend the deadline periodically only under the exact `(tenant_id, channel_id, syncing, sync_run_id, non-NULL lease)` predicate, using database time and checking exactly one affected row. A failed or zero-row heartbeat cancels the run context and stops further work. Ownership rejection returns `sync_ownership_lost`, not partial; a DB failure returns a bounded write-failure class. Never expose SQL, run ID, credential, URL or provider body. Stop and join the heartbeat at the end of the run. A Zalo or legacy run must never gain a lease through heartbeat.
3. The recovery operation may release only a row whose **current** type is allowlisted, status is `syncing`, run ID and lease are both non-NULL, and deadline is expired according to database time. Use a single conditional update per row, including the observed run ID, tenant ID and expired-deadline predicate. Check exactly one affected row. Set status to a bounded error, clear run ID and lease, update attempt time for scheduler throttling, and leave `last_sync_at`, credentials, conversations, messages, attachment references and analysis triggers unchanged. A concurrent heartbeat or terminal write must win or lose atomically; no read-then-unconditional-update.
4. Run bounded recovery scans from the scheduler at startup and periodically, independent of channel due time. A scan/read/write failure leaves the row `syncing` and reports a bounded class. Use a finite batch/limit; do not scan or mutate the active Compose database as part of BUILD. A recovered channel becomes eligible for the ordinary reservation path after its normal throttle; no direct second worker is launched by recovery.
5. On every successful or failed terminal/panic status write owned by a run, clear the lease with the run ID. Preserve the R013/R014 API response and final-write behavior and R015 ownership guard. Do not let an old run reset a newer run's status, deadline or checkpoint. Do not log sensitive predicate values through GORM's interpolated output sink.
6. The allowlist is an audited source contract: if `facebook` or `pancake` sync introduces an outbound mutating request or token rotation, recovery must fail closed until independently reviewed. Do not infer eligibility from metadata or a free-form channel type. No timeout-only takeover for `zalo_oa`, no NULL-ID/NULL-lease recovery, no manual force endpoint, and no blanket startup sweep.

## Acceptance evidence

- Disposable MySQL with synthetic adapters and fake clock/controlled DB time where necessary: admission marker, heartbeat extension, expiry release, scheduler integration, and normal re-admission all hold. Test both supported types and deny Zalo, unknown, old-binary NULL-lease and legacy NULL-ID rows.
- Deterministic races: heartbeat versus release; release versus final status; A paused in a GET or attachment download, then lease expires, B reserves and writes. A must return `sync_ownership_lost`, leave B's data/status/credentials/checkpoint untouched, and not trigger analysis. Include wrong-tenant/forged-ID, DB error and zero-row cases. Tests must detect removal of the type allowlist, run-ID predicate, expiry predicate and R015 write fence.
- Confirm from source that eligible sync adapters only make read requests, and record the in-flight GET and Zalo refresh limitations. Run focused/full backend, build, vet, catalog `-Check`, doctor and diff check. Use no real provider/channel, no persistent Compose DB, and make no CVF governance claim.

## Failure and rollout boundary

If safe lease admission, exact heartbeat, or atomic release cannot be proven, return `BUILD_BLOCKED` without enabling recovery. Rolling back to R015 may leave a leased `syncing` row blocked; it must never make an older binary release it. R016 does not solve Zalo or legacy crash recovery, does not prove worker death, and does not authorize a production rollout, live provider call, push or FREEZE.
