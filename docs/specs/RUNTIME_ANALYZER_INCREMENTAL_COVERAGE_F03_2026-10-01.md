## Intake and design decision

At both report commit `7481196` and current source, ordinary `RunJob` uses `last_message_at > last_run_at`, suppresses conversations when a result's creation time is newer than the last-message time, and loads messages using `sent_at > since`. Successful unlimited runs advance `last_run_at` to completion. Scheduler cron and after-sync invoke this ordinary path. A conversation inserted after selection with an event time before completion can be lost; a later-delivered older message can also remain invisible. Moving only the checkpoint to run start or adding a finite overlap cannot cover arbitrarily late local ingestion; the result-created-time predicate cannot establish that the result saw the current messages.

Use the existing immutable source snapshot as the per-conversation processed-version receipt for **ordinary unlimited incremental runs**. Candidate discovery spans all conversations in the job's tenant/input channels; current full local messages are compared with the latest committed conversation evaluation's validated snapshot for that job. Unchanged source requires no provider call, new evaluation or snapshot. New/changed source remains discoverable independently of event timestamps/checkpoints. This deliberately includes historical never-analyzed conversations and re-evaluates legacy/windowed history once as needed; it increases local discovery/read work, and may increase first-run analysis work. No automatic new rule-version invalidation or provider-quality claim is introduced.

`last_run_at` records a successful scan-start time, not proof that every future ingestion older than that time has been consumed. `job_runs.finished_at` continues to record completion. Discovery plus snapshot version checks, rather than this wall-clock marker, prevent late-data omission. Candidate enumeration is not a transactionally stable global snapshot: rows inserted after discovery and changes after a prepared snapshot are handled on a later invocation. The exact snapshot sent to the provider must be the snapshot persisted for the result.

## Mode boundary

The new contract applies when `fullRerun=false`, `maxConversations<=0`, dates empty, `sinceOverride=nil`, `excludeAnalyzed=false`: ordinary `RunJob` and unlimited `RunJobWithProvider`, reached by cron/after-sync/manual ordinary runs. Name this condition explicitly in code. Full rerun, positive limit, date ranges, unanalyzed and since-last retain their current contracts, including the known F05 defect; do not let zero/full/limit flags accidentally enter the new mode. No API change. Existing single and batch paths must both use the same source-version decision.

## Intended contract

1. For the new mode, do not exclude candidates by `last_message_at`, `last_run_at`, result creation time or `sent_at`. Discover all tenant/input-channel conversations with deterministic ordering (`last_message_at`, then ID; handle NULL without omission). Load the existing full local snapshot (`since=zero`), without changing its format, builder, PII behavior, validation or result-save transaction. No new source/checkpoint schema. Empty current source causes no provider call/result; later messages make it eligible again. Do not label an empty/currently incomplete local corpus as upstream completeness.
2. Resolve the latest committed `conversation_evaluation` for the same tenant, job and conversation (join job_runs with tenant/job checks; deterministic `created_at DESC, id DESC`). A finding row, another job/tenant, an unlinked snapshot or an orphan snapshot alone cannot prove processed source. Reuse `VerifySnapshotProvenance` on a linked snapshot, including tenant/conversation/run identity, digest bytes/schema/message count; compare its canonical digest with the current full snapshot. Equal valid digest skips analysis. Different digest, no evaluation, or a legacy evaluation with no snapshot schedules analysis. A linked snapshot that is missing, misbound, malformed or fails provenance is a verification error, never a successful skip; DB errors fail closed. Do not rewrite old results/snapshots or conceal their source-integrity status.
3. Take the decision at the actual snapshot-load point for single/batch and pass that exact prepared snapshot to transcript generation and `saveResults`. Avoid loading snapshot A for dedupe then snapshot B for the provider. A message inserted/edited after preparation is not falsely represented by the saved snapshot: the next run compares current source and schedules it again. Use one shared helper for the decision; do not duplicate predicates between single/batch. Efficient bounded-size DB lookup chunks are allowed; no new successful truncation/candidate cap. Preserve cancellation responsiveness during local discovery/preparation.
4. Capture the scan-start boundary before candidate selection. On a complete error-free ordinary run, persist `last_run_at` no later than that captured boundary (round down to DB's existing second precision), and store actual completion in finished_at/job.updated_at. Partial, canceled, provider/snapshot/query/result-save failure and failed final persistence cannot advance the checkpoint. Preserve existing success/error/partial/cancelled behavior and positive-limit no-checkpoint contract. Narrow ordinary-run finalization must check tenant-scoped terminal JobRun/job writes, affected rows and retry exhaustion, and avoid advertising successful completion or sending notifications after a terminal persistence failure; use a transaction for coupled run/checkpoint writes. Other modes' selection/checkpoint policy is unchanged. This does not add job execution ownership/single-flight or repair F06 cancellation registry races.
5. Unchanged replay in the ordinary mode adds no new evaluation/snapshot/provider usage for the conversation. Changed late messages with unchanged `last_message_at`, edits to already stored message content, changed selected message metadata/attachments, and a newly ingested older conversation must remain eligible. Use the existing canonical snapshot's supported source fields; unrelated raw-data-only changes excluded by that snapshot are not newly promised. Full rerun continues to permit explicit repeated analysis. Rules changes require the existing explicit full-rerun workflow; no automatic rule digest is added.
6. Scheduler behavior remains bounded to cron/after-sync ordinary execution. A narrow private analyzer/provider/runner test seam may route synthetic provider responses through the real Analyzer for both scheduler entry points. Tests must exercise real job lookup, candidate/snapshot/result/checkpoint writes and after-sync tenant/channel routing; a fake runner that merely records calls is not coverage proof. Disable notifications/pricing fetch in fixtures. No real AI or channel call.
