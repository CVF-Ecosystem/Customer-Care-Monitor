# S1 channel sync single-flight across entry paths

**Tranche:** `CCMAI-RUNTIME-013` · **Phase:** SPEC · **Risk:** R2 · **Entry:** R001–R012 independent REVIEW PASS / FREEZE open; S1 IN_PROGRESS.

## Source finding and decision

Manual `SyncChannelNow` writes `syncing` before launching its goroutine, but the write has no prior-status predicate. Scheduler and `cqa.sync` agent paths enter `SyncEngine.SyncChannel` without reserving the channel. Thus two entries can fetch and persist the same channel concurrently, and a second manual request can return `202 sync_started` while the first run remains active. `SyncAllChannels` also calls `SyncChannel` for each channel. The database channel row is the shared coordination point; a process-local mutex is insufficient when processes share MySQL.

## Contract

1. All four entry paths (manual, scheduler, agent `sync_channel`, agent `sync_all`) must use one tenant-and-channel-scoped atomic admission. It changes `last_sync_status` to `syncing`, clears `last_sync_error`, and updates `updated_at` only if the row exists for the expected tenant and is not already `syncing`. A DB error, missing/changed tenant, or zero affected rows must never start an adapter. Distinguish a genuine busy result from a missing row or DB failure without leaking SQL/credentials.
2. `SyncEngine.SyncChannel` must acquire admission before adapter/credential work. The manual handler must acquire before dispatch and before its existing `202 {"message":"sync_started"}` response, then call an already-admitted execution path that cannot acquire a second time. Repeated manual calls while busy return `409 {"error":"sync_already_running"}` and launch no worker. Keep existing 404 tenant isolation, config-invalid 500, and persistence-failure 500 semantics.
3. Scheduler must skip a busy channel without counting it as synced or overwriting its status. Agent `sync_channel` must report a non-success result with a bounded `sync_already_running` reason. Agent `sync_all` must not report unqualified success if any selected channel was busy; it may continue other channels under existing aggregate-error behavior. Admission failures other than busy are errors, not silent skips. Independent channels may proceed concurrently.
4. An admitted run retains existing success/partial/error checkpoint behavior, but every final status write and manual panic recovery must be tenant scoped and conditional on `syncing`; a worker must not overwrite a missing, transferred or non-syncing row. Do not claim success if the final write fails or affects zero rows. Preserve existing `last_sync_at` success-only behavior and after-sync trigger ordering.
5. Do not auto-expire `syncing` by age or clear it on startup in this tranche. A crash may leave it stuck; define recovery separately with run ownership/lease semantics. This status-only reservation does not establish fencing against a future recovery that clears `syncing` while an old worker remains alive; do not claim that guarantee. Do not change external channel requests, credentials, provider routes, job semantics, UI/API fields beyond the busy response, schema, or migrations. This SPEC makes a runtime concurrency claim from synthetic/disposable tests only, not a CVF governance claim.

## Acceptance

- Disposable MySQL test: concurrent admissions for the same `(tenant, channel)` yield exactly one winner and one busy result; one tenant cannot admit another tenant's channel; a second channel can admit independently. Force a DB write error and a zero-row/missing-row case; neither starts work.
- Manual handler test: first request retains persisted-before-dispatch `202`, second while busy is exact `409` and does not dispatch; config failure, DB error, wrong tenant and panic recovery preserve honest status and bounded responses. A test must detect a regression to an unconditional update or a second acquire in the worker.
- Scheduler and both agent actions: while a channel is busy, no adapter/outbound call, no success count/response and no status overwrite; other eligible channels can still run. Use a deterministic synthetic adapter/transport or a controlled execution seam, with an accepted-run detector so zero-outbound assertions are meaningful. No real channel/provider call.
- Accepted-run completion tests cover success, partial/error, final status write error/zero rows and tenant reassignment. Check that only success advances `last_sync_at` and that after-sync jobs are triggered only after recorded success. Run focused and full backend tests, build, vet, catalog `-Check`, doctor and diff check; record exact results and limits.
