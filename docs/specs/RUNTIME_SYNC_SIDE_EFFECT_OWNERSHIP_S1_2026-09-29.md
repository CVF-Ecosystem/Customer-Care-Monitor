# S1 sync run ownership for persisted side effects

**Tranche:** `CCMAI-RUNTIME-015` · **Phase:** SPEC · **Risk:** R2 · **Entry:** R014-R1 independent REVIEW_PASS / FREEZE_OPEN; S1 IN_PROGRESS.

## Source finding and design decision

R014 fences the final status/checkpoint write with `sync_run_id`. In `backend/engine/sync.go`, a worker that has lost its run can still upsert conversations and messages, update `message_count`, put attachments under a shared `<tenant>/<conversation>/<filename>` key, and persist refreshed Zalo credentials by channel ID alone. A check before an outbound fetch is insufficient: ownership may change before a later DB or object write. A future reclaim must not be enabled on these paths. R015 fences their **local persisted effects** under the existing reservation; it does not reclaim a run or prove that an in-flight provider request cannot occur after ownership changes.

## Contract

1. Carry `SyncReservation` through the entire sync path, including conversation/message upsert, message-count update, attachment publish and Zalo token-refresh persistence. Empty/mismatched reservations fail before work. After ownership loss, stop processing this run with a bounded ownership-lost class; do not turn it into a partial result and keep trying other conversations. R014 terminal/deferred fencing stays intact. Do not expose run ID, credentials, SQL or provider response bodies in returned errors or logs.
2. Each DB side effect of a run must be atomic with an ownership test against the **same** `(id, tenant_id, last_sync_status='syncing', sync_run_id)` row. Use one transaction that locks the channel row and performs the relevant conversation/message/count or credential write before releasing it. A separate check followed by an unlocked write does not meet this contract. The recovery-like generation change in tests must acquire the same row lock through its channel update. Preserve tenant scoping, replay merge rules, exact message-count semantics and accepted-run behavior. A stale run must neither create nor update a conversation/message, change a count, nor replace encrypted credentials. A DB failure must fail closed with a bounded class.
3. Reuse a previously stored `local_path` for the same attachment identity `(type, URL, name)` when that object still exists; an unchanged replay must not create another object every run. A genuinely new download must use a distinct object key per attempt so an old worker cannot overwrite a newer worker's bytes even if both see the same logical filename. Keep existing stored paths valid and the tenant-first path contract used by `/api/v1/files`; do not rename existing objects. A downloaded key may be published in message JSON only through the owned DB transaction. If ownership is lost or publishing fails, best-effort delete only that attempt's new key; if cleanup fails, record an orphan limitation without deleting any previously referenced object. Check ownership before starting another download, use the run's context for HTTP/storage work, and do not claim an already-started external operation is rolled back.
4. Zalo refresh persistence must use the same locked ownership guard and check DB error/row result. Change the adapter callback contract only as needed to propagate persistence failure so it does not silently continue a successful refresh/retry. Reject a stale callback without overwriting current credentials. A provider may already have rotated a token before local persistence fails; this uncertainty must surface as a bounded operational failure and remain a recovery design constraint. No live Zalo request is part of R015 evidence.
5. R015 makes no automatic or manual reclaim endpoint, lease, heartbeat, timeout takeover, startup sweep or direct change to the active Compose database. Legacy `syncing` rows with NULL run ID remain blocked. Mixed old/new binaries are not safe for takeover because an old worker lacks these guards; deployment/recovery design must account for this. R016 or later must establish worker-death proof or close the remaining provider/in-flight boundary before any reclaim is authorized.

## Acceptance

- Disposable MySQL with synthetic adapters and storage: accepted run persists/replays conversations/messages/count and a token callback with the current run ID; no regression to R003 replay or R013/R014 admission and final status behavior.
- Controlled two-generation race: pause A before each category of local write, simulate a release only in test, reserve B, then resume A. A's DB writes are absent; B's rows, count, credentials and final status stay unchanged. Race a channel ownership update against an in-progress write transaction to prove row-lock serialization, not just a precheck. Test wrong tenant, forged/NULL ID and forced DB failure.
- Attachment race with the same logical filename: B's referenced bytes and path remain correct when A's earlier download completes late; no shared-key overwrite and no stale `local_path` publication. Verify legacy paths still resolve, and unchanged identity reuses an existing object without another download. Test best-effort cleanup only for newly created keys.
- Zalo refresh callback test uses a synthetic transport or direct callback seam, never the real endpoint. Detect a stale credential write and a DB write error, and verify a failed persist stops adapter retry. Do not treat synthetic provider output as CVF governance proof.
- Run focused and full backend tests on disposable MySQL, `go build ./...`, `go vet ./...`, catalog `-Check`, project doctor and diff check. Evidence lists every local write path, independent race controls, mutation detectors, resource cleanup, mixed-version and token-rotation limits. Return `BUILD_BLOCKED` if the contract cannot be met within scope.
