## Current contract and gap

R102 persists an immutable local observation and a request with `AWAITING_EXECUTION_AUTHORITY` / `NOT_RUN`; its request-key replay proves only the original intent and rechecks current membership. New requests lock membership, job, channel, conversation, messages, case and original snapshot, then verify latest complete revision and current local digest. It rejects a case with any proposal or an existing request for that revision. None of this grants execution. [intervention_waitdata.go:78-112,155-219,270-410](../../backend/engine/intervention_waitdata.go); [intervention_waitdata.go:5-49](../../backend/db/models/intervention_waitdata.go).

`RunManual` creates or replaces a stable tenant/job/conversation/use-case case, rejects human ownership, reserves its own JobRun, and can spend a budget before one physical provider call. Therefore invoking it after clearing an owner, event or history would violate the existing contract. Its publication binds proposal to current case run/snapshot and rechecks local source. [intervention.go:55-110,132-210,217-315](../../backend/engine/intervention.go). M3 action checks the exact current case version/snapshot and proposal revision/run/snapshot; a new proposal stored without updating the case's reviewable projection cannot be acted on. [intervention_m3.go:82-146](../../backend/engine/intervention_m3.go). Detail currently reads one case and all proposals/events in revision order; the response does not identify an active proposal separately. [api/intervention.go:109-131](../../backend/api/handlers/intervention.go).

## Intended minimal path (future R2 build)

1. Proposed `POST /intervention-cases/:caseId/rerun-requests/:requestId/execute` accepts exactly JSON `{ "expected_case_version": positive_integer, "grant_id": UUID }` (maximum 512 bytes, unknown/trailing fields rejected). Tenant/actor come only from authentication; provider, prompt, run, snapshot, budget and secret are never client fields. Route middleware requires `intervention_cases` read/write and jobs write, with locked service recheck. New claim returns 202 with execution ID/state; current-permission-safe replay returns 202 while pending or 200 terminal; malformed 400, unauthorized 403, missing 404, stale/occupied 409, storage failure 503. `GET` status may be added under the same read permission, but is not needed for admission. Existing R102 request create/replay remains immutable intent-only. A grant is separately **server-provisioned**, with no public issuance route: tenant/job/case/request/revision, provider/model/policy/prompt configuration reference, deadline, issuer/evidence and `ISSUED→CONSUMED` state. This API/grant is proposed behavior, **not current authority**. [api/router.go:199-208](../../backend/api/router.go); [api/intervention_waitdata.go:21-50](../../backend/api/handlers/intervention_waitdata.go).
2. Implement a new **transaction-aware coordinator admission primitive**; the current `ReserveJobRun` is unchanged and unsuitable because its admission commits before a claim [job_run_ownership.go:110-190](../../backend/engine/job_run_ownership.go). Canonical execute-body hash is SHA-256 of a server-encoded fixed-field object `{tenant_id,case_id,request_id,expected_case_version,grant_id}` with canonical UUID case and integer encoding; store it on the execution row. First validate JSON and recheck *current* membership and tenant/request ownership, then read an existing execution by `(tenant,request)` and compare that hash **before** stale version, human-state or unused-grant checks. Equal replay returns that execution's status even after successful case-version change; differing hash conflicts. No new local owner or durable effect occurs for replay. For a new claim only, the local owner map reserves tenant/job before DB; losers get no durable run. One DB transaction locks tenant parent, current actor membership, job, channel, conversation/messages, case and original snapshot, then request/revision/grant; it rechecks `intervention_cases` read/write, jobs write, manual active intervention job, server-marked synthetic Pancake channel in job inputs, all tenant/source identities, original provenance, case version/human state, complete selected revision/current local digest, no proposal, unused unexpired grant. It rechecks existing execution/hash under locks against races. Only then it inserts one `running` JobRun, new run-owned snapshot and execution claim, consumes grant, and CAS-sets the case's active-execution pointer. Commit is the single admission point. A second process locks the same job/case and returns existing claim status or conflict with **zero new persisted run/debit/call**. If the caller merely sees an uncertain DB commit result, query the unique request/claim/run identity: a confirmed committed row is governed by its persisted state; an unresolved result is a caller-side `ADMISSION_UNCERTAIN` hold, **not** an invented durable state/receipt, with no call/readmission. The new primitive preserves existing Job→JobRun serialization and local owner cancellation; owner-map release follows failed/no-op admission. [job_run_ownership.go:19-34,114-190,317-342](../../backend/engine/job_run_ownership.go).
3. Proposed schema: `InterventionExecution` with ID, tenant/case/job/conversation/request/revision/grant/run/actor IDs, canonical execute-body hash, original snapshot/run/digest, claimed run snapshot/digest/manifest binding, expected and claimed case version, provider configuration reference, state, timestamps and terminal code; unique `(tenant_id,request_id)`, `(tenant_id,run_id)`, `(tenant_id,grant_id)`. A nullable `InterventionCase.ActiveExecutionID` is CAS from NULL to claim ID at admission and remains occupied through a terminal manual hold; MySQL row lock plus `WHERE version=? AND active_execution_id IS NULL` is the active-case exclusion (no partial unique index assumed). Grant has unique `(tenant_id,request_id)` and PK ID. `InterventionAttempt` remains unique by run; add `execution_id` unique for traceability. Add `InterventionCase.ActiveProposalID` nullable after migration; previous rows read as NULL. No historical row is erased. Preserve original WAIT_DATA projection until publication; original pointers live in immutable execution/revision/request/snapshot/event rows. [models/intervention.go:16-112](../../backend/db/models/intervention.go); [models/intervention_waitdata.go:5-49](../../backend/db/models/intervention_waitdata.go). State CAS permits `CLAIMED→CALL_MAY_HAVE_STARTED→RESPONSE_RECORDED→PUBLISHED` or one terminal failure. Terminal claim cannot restart. Existing R102 one-request-per-revision and unchanged-source revision rule mean a failed/uncertain call **cannot** simply create a new request on the same revision/source [intervention_waitdata.go:283-304,394-405](../../backend/engine/intervention_waitdata.go); it remains a manual hold pending separately designed authority, never an automatic retry.
4. The pre-call short transaction rechecks current actor/job/case/source under the same order and verifies the grant is **CONSUMED by this execution**, still within its deadline and configuration binding. It locks stable budget, debits once and inserts one attempt, and CAS-marks `CALL_MAY_HAVE_STARTED` before invoking transport. Marker commit is the permission/source authorization linearization point. If a check fails before it, terminalize claim and owned run with **zero debit/call**. Revocation or source change after marker may still incur this one call; publication rechecks and must reject a no-longer-authorized/current result. A missing cap denies; consumed cap never auto-refunds [intervention.go:186-210](../../backend/engine/intervention.go); [models/intervention.go:5-30](../../backend/db/models/intervention.go). A crash after the durable marker is a possible external call regardless of whether transport actually started. Use existing one-call transport, output/evidence validation and usage-presence settlement semantics [intervention.go:217-253,318-401](../../backend/engine/intervention.go). No DB transaction/row lock spans the network call.
5. `CLAIMED` before call is recoverable only by an explicit terminal no-call check under locks; no automatic rerun. `CALL_MAY_HAVE_STARTED` without durable response becomes `RECOVERY_REQUIRED` with consumed budget, unknown attempt/usage and blocked JobRun disposition, pending operator review. `RESPONSE_RECORDED` stores response metadata/usage presence, **not** a durable validated proposal body. Only the original still-live owner retaining the validated response may retry its failed **DB publication** under fresh locks/source checks; restart or owner loss is a manual hold with no reconstructed proposal, receipt or provider replay. Terminal states `PUBLISHED`, `DENIED`, `STALE_SOURCE`, `OUTPUT_INVALID`, `PROVIDER_UNKNOWN`, `SETTLEMENT_FAILED`, `CANCELLED`, `RECOVERY_REQUIRED` are CAS and immutable except separately reviewed correction. One terminal receipt and run status are committed atomically with state where possible; failed terminal commit leaves a blocking running row and manual hold. The current coordinator deliberately fails closed on ownerless running rows and has no distributed recovery [job_run_ownership.go:19-34,263-310](../../backend/engine/job_run_ownership.go). This slice does **not** promise orphan reclaim or a new request after uncertainty. Do not promise exactly-once provider effects.
6. Publication is one short transaction under owner cancellation serialization, with lock order tenant → membership → job → channel → conversation/messages → case → original/run snapshot → request/claim → attempt/proposal/receipt → JobRun. Recheck current permission, job/channel/source identities, owned run, claimed case version, active execution pointer, selected revision, no competing proposal/human mutation and current local source digest against the claimed snapshot. If anything changed, keep original WAIT_DATA projection and consumed attempt/usage; commit terminal failure/receipt/run separately under the same lock order, with no proposal. An already observed provider response may cost money even when publication fails. No DB lock spans the network call.
7. On success append one proposal with `CaseID` of the **same** original case, new run-owned snapshot, run ID and a unique revision equal to the case's next version. Atomically advance that case's current projection to `ELIGIBLE` / `LLM_SUCCEEDED` / `PENDING_REVIEW` / `OPEN`, new run/snapshot IDs, current version and policy/prompt, while retaining original provenance in immutable revision/request/execution records and preexisting human events. Append an execution receipt/event with old and new projection/lineage. Update detail to identify `active_proposal_id` and retain ordered proposal/history output. For a legacy case with `ActiveProposalID=NULL` **and** `ActiveExecutionID=NULL`, M3 may resolve exactly one proposal matching tenant/case plus the current case run/snapshot/digest and requested proposal ID/revision; ambiguity or mismatch fails closed. A locked conditional pointer backfill without version/history rewrite is allowed after that exact match. For any new execution, the action must require its explicit active pointer and never fall back to an old proposal. Preserve legacy CONFIRM/CORRECT/REJECT, assignment and outcome transitions with the existing source/version checks. [models/intervention.go:32-112](../../backend/db/models/intervention.go); [api/intervention.go:109-131](../../backend/api/handlers/intervention.go); [intervention_m3.go:120-146](../../backend/engine/intervention_m3.go). The projection migration leaves existing case rows/history intact and permits a nullable active-proposal pointer.

## Source writers and scope boundary

The supported sync engine writes conversations/messages/counts through `withOwnedSyncWrite`, locking the channel [sync.go:164-200,622-761](../../backend/engine/sync.go). R102 and M3 lock that channel before reading messages [intervention_waitdata.go:152-219](../../backend/engine/intervention_waitdata.go); [intervention_m3.go:97-140](../../backend/engine/intervention_m3.go). In contrast, `DeleteChannel` and `PurgeChannelConversations` lock conversations then delete snapshots/messages without a channel lock [api/channels.go:260-296,319-373](../../backend/api/handlers/channels.go); `ResetDemoData` locks conversations then JobRuns and deletes source/run/usage [api/demo.go:430-475](../../backend/api/handlers/demo.go). `DeleteJob`/`ClearJobRuns` use `GuardJobMutation` then delete runs/snapshots [api/jobs.go:211-249,314-342](../../backend/api/handlers/jobs.go). They do **not** currently satisfy the proposed executor lock order.

Future minimum integration: add an early tenant-scoped intervention-lineage fence to delete/purge/reset/job-delete/clear-runs before their existing lock sequence; reject while claim is active **or** in manual hold, and reject deletion of any linked original/run snapshot, run, case/history, attempt or receipt even after terminal state unless an independently designed archival path preserves complete lineage. To avoid a check/write race, admission and destructive paths both lock the Tenant parent first, then Job, then Channel, before Conversation/JobRun and an existence check under those locks. Revise old delete paths to this order where they touch these parents; preserve membership lock immediately after Tenant in execution transactions. The sync write's channel lock remains the source serialization point. No out-of-band SQL or upstream history currentness claim; real channel adapters remain outside this synthetic case path. Denial must leave all source and intervention provenance rows unchanged. This fence is a specified implementation requirement, not current behavior.
