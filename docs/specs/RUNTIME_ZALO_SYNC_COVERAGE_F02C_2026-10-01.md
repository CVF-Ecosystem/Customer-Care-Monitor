## Intake and design

`backend/engine/sync.go` still asks Zalo for 100 conversations. `backend/channels/zalo_oa.go` stops successfully at that cap or a short page; missing/null/malformed data becomes an empty success. Invalid rows are skipped, missing IDs/timestamps become empty/zero values, and no finite traversal budget exists. A truncated success can advance `last_sync_at`. This is a source defect, not an observed real-Zalo incident. Zalo also has a single-use refresh POST, persistence-before-in-memory replacement and no automatic lease recovery; preserve these contracts.

Primary sources retrieved 2026-10-01:

- The [official PHP SDK example](https://github.com/zaloplatform/zalo-php-sdk/blob/master/README.md) uses JSON `data` with `offset=0,count=10` for recent chats. It does not establish terminal-page or snapshot guarantees.
- The [official conversation-message reference](https://stc-developers.zdn.vn/docs/v2/official-account/tin-nhan/quan-ly-tin-nhan/lay-thong-tin-tin-nhan-trong-mot-hoi-thoai) describes offset as the first returned message index, count up to 10, src 0/1 and an example with millisecond timestamps and string IDs. This describes `/conversation`; it is not a retrieved full contract for `/listrecentchat`.

The existing recent-chat response mapping, millisecond time interpretation, count 10 and absolute row-index offset are inherited assumptions. For a short nonempty page, advance offset by its physical row count; do not skip unobserved rows. Only a valid empty array establishes application-level traversal completion. This conservative policy may cause an error on a provider that signals exhaustion differently. Offset traversal cannot prove a stable snapshot under concurrent insertions/reordering: deduplication, cycle detection and a fetch-start checkpoint reduce specific risks but cannot eliminate that residual. Keep live coverage OPEN; do not silently substitute a cursor/API version or claim provider completeness.

## Intended contract

1. Engine requests exhaustive mode (`limit <= 0`) for `zalo_oa`, as for Facebook/Pancake; unknown types retain their existing limit. A positive direct-call limit must fail with an incomplete-coverage error if the eligible unique result exceeds it. Never return a capped success. Keep the shared adapter interface and schema.
2. GET the existing `/v2.0/oa/listrecentchat` with count 10. Accept the existing direct `data: []` and nested `data: {data: []}` forms only when an explicit array is present in a successful envelope. Missing/null/non-array data, non-object rows, invalid src (only integral 0 or 1), missing/invalid selected customer ID, or invalid time fails the run, including on old/duplicate rows. Preserve exact nonempty string IDs, never float-convert large IDs. Time must be a positive integral millisecond timestamp, without overflow, truncation or unsupported calendar values. Validate every physical row before filtering.
3. Include unique customer conversations at `LastMessageAt >= since` (zero since means no lower bound), without assuming ordering or stopping at an old row. Dedupe by selected user ID, retain the newest valid timestamp and its associated metadata; use deterministic tie handling. Preserve src-direction/name mapping. Continue after every nonempty page with offset increased by the physical row count, including filtered or duplicate rows. Success requires an explicit empty page. Detect repeated page/cycles using stable row identity/time rather than arbitrary metadata; enforce a finite **500-requested-page budget**, counting the terminal page. Budget exhaustion, repeated pages, cancellation before/after a response, decode/read/network/API/HTTP errors and positive-limit overflow return an identifiable incomplete-coverage error. A partial slice is never success.
4. Bound response bodies to **8 MiB** before decoding, close them on every path, reject non-2xx responses and malformed success/error envelopes. Preserve the existing at-most-one refresh and one original-request retry on `error=-216`; no new network retry policy. Refresh success needs a valid nonempty token pair before callback. Callback persistence succeeds before in-memory replacement or retry. Persistence/ownership failure keeps old tokens and stops retry. Preserve `errors.Is` for callback and context errors using a safe wrapper whose displayed text does not reveal the cause. Do not change OAuth endpoint, request query/body/header protocol, single-use semantics, or engine ownership fences.
5. Request/read/decode/API/refresh/callback errors and logs must omit raw URLs, response bodies, provider message strings, all token values and AppSecret. Safe status/numeric code/context classes are allowed. Narrow shared request/refresh helper hardening is in scope; `FetchMessages` selection, pagination, attachment mapping and its no-since-filter behavior are unchanged. Do not broaden `extractZaloDataArray` semantics for messages merely to implement strict conversation parsing.
6. On Zalo success, bound `last_sync_at` by the timestamp captured immediately before conversation fetch, using the existing conservative second truncation; keep actual completion in `updated_at`. Existing one-hour overlap remains. Failure, partial slice, lost ownership or per-item write failure cannot advance the previous checkpoint or trigger after-sync. Facebook/Pancake limit/checkpoint behavior is preserved. Zalo remains excluded from R016 automatic lease recovery.

## Acceptance evidence

- Real Zalo adapter with a synthetic transport: >130 eligible unique IDs, direct and nested arrays, src both directions, IDs larger than float precision, a short nonterminal page, interleaved old rows, exact-since row, duplicates and an empty terminal page. Assert the exact eligible ID set/newest metadata and each requested offset/count; no real endpoint contact.
- Negative table: invalid envelope/data/row/src/ID/time (including filtered rows), non-2xx/429, transport/read/JSON/API error on a later page, repeated page/cycle, budget exhaustion, limit overflow, oversized response and cancellation at terminal response. Each returns error and never token/URL/body/provider-message text. Pair negative observers with positive controls.
- Synthetic refresh proof: `-216 -> refresh -> persisted pair -> retry same offset` succeeds; refresh HTTP/decode/provider/invalid-token failure and persistence/lost-ownership failure stop. Preserve the existing `TestZaloRefreshPersistenceFailureStopsRetry` assertions, callback `errors.Is`, request count and unchanged old tokens. Probe credential-bearing malicious errors in both original GET and refresh POST without printing fixture values into evidence.
- Disposable MySQL with real adapter/synthetic transport: >100 conversations/messages stored; later-page failure keeps prior checkpoint and zero after-sync calls; retry/replay idempotent; delayed success bounds checkpoint by fetch start while completion is later. Verify all three channel limits and Facebook/Pancake checkpoints; rerun R012–R016 persistence/ownership/lease regressions, including Zalo exclusion.
- Demonstrate an old-source failure or reversible mutation for cap/short-page/malformed-data/checkpoint and refresh-persistence assertions. Record exact commands/results and restore temporary probes. Full uncached backend tests with disposable MySQL and R019 five-sentinel gate, backend build, repository preflight, catalog and doctor are required. Synthetic tests assert application sync behavior only, not AI governance or real-Zalo completeness.
