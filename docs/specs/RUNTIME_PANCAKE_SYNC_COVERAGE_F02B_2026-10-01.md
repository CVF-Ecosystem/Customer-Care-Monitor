## Source finding and design decision

`SyncReservedChannel` still sends `limit=100` for `pancake` (`backend/engine/sync.go`); `PancakeAdapter.FetchRecentConversations` returns success as soon as that many eligible rows have been appended (`backend/channels/pancake.go`). It also treats a short page, a repeated cursor and exhaustion of its 200-page loop as success, and a missing/malformed `conversations` field becomes an empty terminal page. `until` is recalculated on every page. A run can therefore advance `last_sync_at` after incomplete coverage. This is a local source risk, not a verified live Pancake incident.

The official OpenAPI describes a v2 conversation endpoint with at most 60 conversations per call, pagination by `last_conversation_id` using the last row of the prior call, and `since`/`until` timestamp filters. It does **not** state that a short page proves the end of the cursor chain. R023 therefore uses an observed empty page as the terminal proof, with a finite fail-closed page budget. Since `until` is a fixed upper bound for the fetch, the successful Pancake checkpoint must be no later than the fetch-start lower bound, rather than the run's finish time. This preserves the next run's overlap for updates arriving while a long run is processing.

## Intended contract

1. The engine requests exhaustive mode (`limit <= 0`) for `pancake`; Facebook remains exhaustive and Zalo retains 100 until its own tranche. A positive adapter limit, when called directly, must return an incomplete-coverage error if more eligible conversations exist, never a truncated success. No adapter-interface or DB-schema change is authorized.
2. Capture one fixed `until` before Pancake page 1 and reuse it on every page, including retries. Keep the existing `since` and `type=INBOX` query contract. Traverse by the **last physical response row's** ID, including pages containing filtered COMMENT rows; continue after any nonempty page, even one shorter than 60. Success requires an explicit empty `conversations` array after a valid cursor chain. Missing/null/non-array `conversations`, empty/malformed row ID or `updated_at`, repeated cursor, page failure, cancellation, or the finite page budget before an empty page returns an incomplete-coverage error. Inspect all rows; eligible INBOX rows at `updated_at >= since` are included, older rows skipped without assuming row order, duplicates handled deterministically. Existing metadata redaction and message mapping stay intact.
3. On successful Pancake sync, `last_sync_at` is bounded by the timestamp captured immediately before conversation fetch, rounded down to the provider filter's second precision. The terminal status write remains ownership-fenced and records its actual `updated_at`; only the success checkpoint is bounded. A fetch error (including a partial slice), per-conversation failure, lease/ownership loss or budget error must not advance the prior success checkpoint or fire after-sync. Preserve the R013–R016 behavior and one-hour overlap. The clock-boundary proof may use a narrow test seam in `sync.go` if necessary, without changing the shared adapter interface.
4. Never log or return the page token, raw token-bearing URL or response body on request/API/read failures. Error text may retain safe status/code/context class. This applies to the shared Pancake request helper, but does not authorize changes to `FetchMessages` selection/pagination behavior. Real endpoint response shape, concurrent provider updates and rate limits remain outside synthetic proof.

## Acceptance evidence

- Synthetic Pancake transport proves 130+ distinct eligible INBOX conversations across at least three nonempty pages and an empty terminal page, with a short nonterminal page, interleaved COMMENT/older rows, an exact-`since` row and a duplicate ID. Assert each eligible ID once, the physical-row cursor, unchanged `since`/fixed `until` on every request, and no contact with a real endpoint. Show an old-source assertion or reversible mutation fails before repair.
- Negative cases: malformed/missing/null `conversations`, malformed ID/time (including on a skipped row), repeated/nonprogressing cursor, API/429 exhaustion/read/decode/network failure on a later page, cancellation, positive-limit truncation and 200-page budget. Each must return non-success without a token/URL/body in error/log text. An actually empty array is the only accepted terminal page. Keep a positive control for each synthetic observer/transport.
- Disposable-MySQL engine tests using the real Pancake adapter and synthetic transport store >100 conversations and messages; a later-page failure leaves the previous `last_sync_at` and zero after-sync calls; retry/replay are idempotent. A delayed successful run shows the Pancake checkpoint is no later than fetch start while `updated_at` reflects completion, and the next run's overlap can see an update made during the first run. Assert Facebook remains exhaustive, Zalo remains 100 and R013–R016 regressions still pass.
- Run focused tests, full backend suite on disposable MySQL with the R019 five-sentinel gate, `go build ./...`, downstream preflight, catalog check, doctor and diff check. Record commands, counts, cleanup and limits. Do not use the persistent Compose DB or real Pancake token. Synthetic tests prove application semantics only; they do not prove live Pancake completeness or CVF AI governance.
