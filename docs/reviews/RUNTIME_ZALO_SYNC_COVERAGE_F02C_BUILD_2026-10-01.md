## Source trace before the change

- Engine (`engine/sync.go`): `conversationFetchLimit("zalo_oa")` = **100**; on a fetch error `finish("error")` before any conversation is processed; on success `last_sync_at` = completion time (`boundsCheckpointByFetchStart` was Pancake-only). Zalo installs `SetTokenRefreshCallback` → `persistZaloRefreshedTokens` (ownership-fenced; returns `ErrSyncWriteFailed`/`ErrSyncOwnershipLost`, which the engine recognizes with `errors.Is`). Zalo is not lease-eligible.
- Adapter (`channels/zalo_oa.go`), `FetchRecentConversations`: returned **success** when the count reached `limit`, when a page had fewer than 10 rows, and when `extractZaloDataArray` found no array (missing/null/malformed `data` → empty → terminal). Non-object rows were skipped; `src` defaulted to the customer-sent branch for any non-0 value; a missing ID became `""`; a missing/non-numeric `time` became the zero time; the offset always advanced by 10; there was no page budget or dedupe. All numbers went through `float64`. The old `since` comment said filtering was left to the DB.
- `doRequest`: no body bound, any status accepted, error text included the provider `message`, transport errors kept the `*url.Error` text (the access token is a header, not in the URL, but custom transports and the refresh POST — whose query carries `refresh_token` — can echo values), and a debug log printed the endpoint URL and the response keys. `refreshToken`: transport/decode errors kept their cause text, provider `message` was shown, an empty token pair was passed to the callback and then installed, and the callback error was wrapped with `%w` (text included).

**Primary-source reconciliation.** I did not re-fetch any Zalo document in this BUILD (no external call); I relied on the SPEC's record (official PHP SDK recent-chat example with `offset`/`count=10`; the conversation-message reference describing absolute offset, count ≤ 10, src 0/1, millisecond times, string IDs). Inherited, unproved assumptions kept unchanged: the listrecentchat response mapping (direct `data: []` or nested `data.data`), millisecond `time`, count 10, absolute **row-index** offset, and `error: 0` as success. A provider that signals exhaustion differently than an empty array would now fail the run (conservative, per SPEC).

## Implementation

`backend/channels/zalo_oa.go`
- `FetchRecentConversations`: requests `/v2.0/oa/listrecentchat` with `{"offset":N,"count":10}` (unchanged protocol). After every **nonempty** page the offset advances by the page's **physical row count** (short pages continue); only an explicit empty array ends successfully. Each page is decoded with `UseNumber` and validated **before** filtering: JSON object, integral `error` present and 0, `data` an explicit array or `data.data` an explicit array; every row an object with integral `src` 0 or 1, the selected customer ID (`to_id` for 0, `from_id` for 1) a nonempty string, and `time` a positive integral millisecond value ≤ 9999-12-31. Large numeric values stay exact; IDs are only accepted as strings.
- Eligible: `LastMessageAt >= since` (zero `since` = no lower bound); no ordering assumption. Duplicates by customer ID keep the newest time with its name/metadata; a tie keeps the first seen. Output order is first appearance.
- `ErrZaloCoverageIncomplete` (rows returned only for diagnostics, wrapping the cause with `%w`) for: any request/page error (HTTP, transport, read, decode, API, refresh), a page whose rows (`customer@time`) equal an earlier page, cancellation before a request **or after a response** (including the terminal page), a positive `limit` the unique window exceeds (exactly `limit` rows returned), and the **500-requested-page** budget (the terminal page counts).
- Shared helpers: `doRequestRaw` (bounded **8 MiB** read via `LimitReader` + length check, body closed on every path, non-2xx rejected, malformed envelope / non-integral `error` rejected, `-216` → at most one refresh and one retry of the same request, no other retry). `doRequest` decodes the same bytes into the old `float64` map, so `FetchMessages`/`HealthCheck` keep their exact mapping, selection and pagination. Errors show only fixed text or numeric codes: provider `message`, URLs, bodies, tokens and AppSecret are never included; transport/callback/context causes stay reachable through `zaloSafeError.Unwrap` (`errors.Is` works, `Error()` hides them). The request log prints only the endpoint name, status and length; the per-page debug log with response keys was removed (`mapKeys` deleted with it).
- `refreshToken`: same endpoint, query, header and single-use semantics; body bounded and non-2xx rejected; provider error code only; a **nonempty access/refresh pair is required before the callback**; the callback (persistence) still runs **before** the in-memory replacement, and on failure the old pair is kept and no retry happens.

`backend/engine/sync.go`: `conversationFetchLimit` returns 0 for `facebook`, `pancake` and `zalo_oa` (unknown types keep 100); `boundsCheckpointByFetchStart` is true for `pancake` and `zalo_oa`, reusing the R023 fetch-start checkpoint (second-truncated `syncNow()` captured before the fetch; `updated_at` keeps completion). No ownership, lease or status-fencing change; Zalo stays excluded from lease recovery.

## Behavior changes and limits for the reviewer

1. A Zalo run now ends `error` (keeping the previous checkpoint) unless the offset walk reaches an explicit empty array within 500 pages (~5k conversations at 10 per page), and whenever any row — including old or duplicate ones — is malformed. No cursor/API-version change was made.
2. Each successful window costs one extra request (the empty terminal page); short pages no longer stop early. The checkpoint is now the fetch start, so the next window re-reads conversations touched during the run; upserts keep this idempotent.
3. Error texts changed: provider messages and transport causes are no longer displayed (numeric codes/fixed classes only). `doRequest` now rejects non-2xx and oversized/malformed responses for `FetchMessages`/`HealthCheck` too (shared helper hardening allowed by SPEC); their mapping and paging are unchanged.
4. **Not covered:** offset stability under concurrent inserts/reordering on real Zalo (dedupe, repeat detection and the fetch-start checkpoint reduce but cannot eliminate it), provider retention/access limits, and complete message coverage (`FetchMessages` unchanged). Synthetic responses and disposable MySQL prove local application behavior only — not CVF AI governance or real-Zalo completeness. F02 stays OPEN.
