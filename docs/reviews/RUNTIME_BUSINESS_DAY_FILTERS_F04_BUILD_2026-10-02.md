## Source trace and the storage check (mandatory first step)

- Backend at base: `dashboard.go` used `now.Truncate(24h)` (UTC), `time.Parse` UTC dates, inclusive `BETWEEN from AND to-1s`, `DATE(created_at)` buckets on the stored wall time, and lower-bound-only today/month costs; `results.go` parsed UTC dates with an inclusive last-second upper bound (list, counts and CSV/XLSX share `baseQuery`); `cost_logs.go` used raw `from+" 00:00:00"` / `to+" 23:59:59"` strings; `conversations.go` message export parsed UTC dates with the same last-second bound. Frontend: `Dashboard.vue` and `Results.vue` built presets from browser-local `new Date(y,m,d-N)` then `toISOString()`, with 7 and 28 presets of 8 and 29 dates; `Messages.vue` defaulted to UTC ISO dates; CostLogs sent raw input strings.
- **Driver/storage facts verified in the vendored sources** (no assumption): `config.go` builds `parseTime=True&loc=Local` (Compose runs the app with TZ Asia/Ho_Chi_Minh); disposable test DSNs use `loc=UTC`. `gorm.io/driver/mysql@v1.6.0` opens the DSN unchanged and `go-sql-driver/mysql@v1.8.1` converts every bound `time.Time` with `cfg.Loc` before serialization and decodes DATETIME in `cfg.Loc`. Timestamp columns are GORM `time.Time` (datetime(3)). Therefore the stored wall time depends on the driver location (asserted below), a typed instant keeps whatever location the connection uses, and **raw `DATE(col)` on the wall time is only correct when the driver location is Vietnam**. No storage encoding was unidentifiable or mixed in this repository; nothing was migrated or reinterpreted, so no `BUILD_BLOCKED`.
- **Chosen aggregate strategy:** bucket by comparing the column with typed day-boundary instants (`CASE WHEN col >= b_i THEN i … ELSE 0 END`, 31 days, rows pre-restricted to `[today-30d, tomorrow 00:00)`), grouped by the bucket alias, then map bucket → Vietnam date key in Go. Cost: one grouped scan per series over the tenant's rows in the same 31-day window the `DATE()` version scanned, plus a 31-way CASE evaluated per row (+30 bound parameters); no named-zone tables, no session `time_zone`, no DSN change, no row loading into memory.

## Implementation

Backend (`backend/api/handlers`):
- **`business_dates.go`** (new): fixed zone `pkg.VNLocation`; `parseBusinessRange(from,to)` → `[From, ToExclusive)` as typed instants. Strict `YYYY-MM-DD` (rejects `2026-1-2`, `2026-10-02x`, spaces, `T…Z`, impossible dates, `1000-01-01`-before and `9999-12-31`-after DATETIME limits, and a reversed pair), empty side open, equal dates = one full day. `requestBusinessRange`/handlers answer **400 `{"error":"invalid_date_range"}` before any query or file output**. `businessRange.where(q, col)` applies `col >= From AND col < ToExclusive`. `businessClock` is the private request-clock seam.
- **`dashboard_business_day.go`** (new): `newDashboardWindow(now)` derives todayStart/tomorrowStart/monthStart/nextMonth/seriesStart (= today − 30 calendar days → 31 dates) from one instant; `dashboardRange` (no dates → `[todayStart, tomorrowStart)`; an explicit side leaves the other open); `dashboardCostSum`, `dashboardCostByDay` (newest first, as before) and `dashboardMessagesByDay` (oldest first; count, distinct customer `chat_count`, agent `reply_count` unchanged in meaning).
- **`dashboard.go`**: all date-dependent queries use the helpers and `.Error` is checked; any failure is the generic `500 {"error":"dashboard_unavailable"}` (the existing QC-count failure contract is preserved and covered). `cost_today` and `cost_this_month` are bounded above (day / month); `issues` vs `qc_violation_count` meanings unchanged.
- **`results.go`**: `parseResultFilter` now returns an error; `ListResults` and `ExportResults` answer the 400 before any file bytes; list, counts and CSV/XLSX share one interval; `date_field=conv|eval` unchanged. `formatResultTime` prints on the Vietnam calendar (exports used to print the driver's zone) so the exported dates match the filter.
- **`cost_logs.go`**: list and total share the parsed interval; provider filter and pagination unchanged.
- **`conversations.go`** (message export): both dates still required (existing text); same parser; selects conversations by `last_message_at` and still exports **all messages** of the selected conversations; channel/type filters unchanged.

Frontend:
- **`utils/businessDay.ts`** (new): pure calendar-key arithmetic (`vnToday` via the existing `vnDateKey`, `addDays`, `isoWeekday`, `startOfWeek/Month/Quarter/Year`, `lastDays`, `presetRange`). Today = same date on both bounds; `7days`/`28days` = exactly 7/28 dates including today (intentional change from the old 8/29); week begins Monday; month/quarter/year begin on the Vietnam first day and end today.
- `Dashboard.vue` (default 28 dates, presets), `Results.vue` (`all` stays the default; today/7/28/month use the helper; list and export submit exactly the selected strings with `date_field` and other filters), `Messages.vue` (export default exactly 7 dates, submitted as date strings), `CostLogs.vue` (empty/manual defaults kept): a Vietnam-time label (`vn_date_note`, vi/en) beside the date controls; no global formatter change.

## Behavior changes and limits for the reviewer

1. **Intentional contract changes:** `7days` and `28days` are now exactly 7 and 28 dates including today (they were 8 and 29); the Dashboard default and the message-export default follow; a Dashboard request with no dates is today (it was `today(UTC) .. now`); `to` is now an exclusive-next-midnight bound; an explicit single side leaves the other open; exports print Vietnam times; invalid/reversed/unrepresentable dates are now 400 `invalid_date_range` instead of being silently ignored or falling back.
2. `cost_by_day`/`messages_by_day` keep their 31-date horizon but are now bounded above by tomorrow's Vietnam midnight and bucketed by Vietnam date.
3. Date-dependent Dashboard queries now fail loudly (generic 500) instead of returning zeros; unrelated swallowed errors elsewhere (static counts, onboarding, notification logs) were not touched.
4. **Not covered:** arbitrary legacy rows written under a different driver location than the one running (no row was shifted or inferred); `last_message_at`/`created_at` semantics of other endpoints; the tenant-timezone Settings selector is still inactive and the label says Vietnam time, not the tenant setting; analyzer date/mode selection stays F05; a real browser-to-server run was not performed (UI specs mock the API). Synthetic data proves calendar/query/report semantics only — no provider, upstream completeness or CVF AI-governance claim.
