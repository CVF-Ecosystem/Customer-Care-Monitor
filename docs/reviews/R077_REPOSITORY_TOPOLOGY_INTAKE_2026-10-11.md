## Repository-described deployment surface

The README describes one workspace per installation and instructs operators to build with `docker compose up -d --build`; installation and update guides also describe a source-built Compose deployment and say there is no official image or release channel (`README.md:5-28`, `docs/guide/installation.md:1-37`, `docs/guide/updates.md:1-20`). The Compose example defines one `app` service, a separate MySQL `db` service, `DB_HOST=db`, and `restart: unless-stopped`; it does not specify a replica count. The Dockerfile builds the frontend and one backend binary into an application image (`docker-compose.yml:19-68`, `Dockerfile:10-34`). This is one versioned recipe. “One workspace per installation” does not establish one process, one database writer, a shared database across installations, or what is currently running.

In the source call path, `main` creates and starts a scheduler before starting the HTTP router (`backend/main.go:69-85`). Each process that runs this code therefore enters `Scheduler.Start`. That method registers periodic work, synchronously invokes channel sync-lease recovery, loads cron jobs, calls `cleanupStuckRuns`, and then starts the scheduler (`backend/engine/scheduler.go:58-135`). The order matters: startup has a separate channel-lease write path before the JobRun sweep.

`cleanupStuckRuns` selects every `job_runs` row whose status is `running`, then updates each selected model by its primary key to `failed`, with a finish time and restart message (`backend/engine/scheduler.go:104-128`). The update has no `status = 'running'` condition, tenant/job/run identity predicate, parent lock, affected-row check, or readback. A row that becomes terminal after the query can therefore be overwritten by the later update; this is a conditional source inference, not a reproduced defect.

Job execution ownership is split between a process-local coordinator and persisted admission. The coordinator stores owners in memory; reservation locks the tenant-scoped Job and refuses admission when a `running` JobRun already exists (`backend/engine/job_run_ownership.go:61-90,107-190`). The persisted `JobRun` model has no owner, lease, heartbeat, or fencing field (`backend/db/models/job.go:48-60`). An owner is released after the worker's last effect, including notification completion (`backend/engine/analyzer.go:47-72,411-420`). A process-local owner map cannot establish the state of another process.

The ordinary finalizer is a distinct path: it locks Job then JobRun, requires the exact row to remain `running`, writes and reads back terminal state, and uses a best-effort exact-still-running error fallback without checkpoint advancement (`backend/engine/analyzer_incremental.go:167-284`). That fallback does not check the affected-row count or read back its result, so an abort/finalizer error alone does not prove the stored row remains `running`; R076 preserves this limitation. Startup rewriting must not be justified by treating every finalizer error as a stranded row.

Channel sync-lease recovery is separate from JobRun ownership. `Scheduler.Start` calls it synchronously, and it can update eligible Channel rows under the R016 GET-only allowlist and exact lease/status/run predicates; it does not release JobRuns (`backend/engine/scheduler.go:82-95`; `backend/engine/sync.go:1166-1221`; `docs/specs/RUNTIME_SYNC_LEASE_RECOVERY_READ_ONLY_S1_2026-09-29.md:7-24`). Future startup tests must allow and separately identify that existing Channel behavior rather than infer that scheduler startup is write-free.

If multiple app processes share a database, one process's startup sweep could mark a row failed while another process still owns the run. Provider and result writes can precede finalization, so a second admission could overlap old-run effects (`backend/engine/analyzer.go:245-329`). This requires the shared-database/overlapping-writer topology and matching source behavior; neither is known for a deployment, and the risk has not been reproduced. The source also permits a terminal-race overwrite as described above. Root supplied these startup/finalizer pointers and the conditional race scenarios; the worker independently inspected and hashed the cited source. These are source inferences, not incidents or autonomous-discovery claims.

## Feasible fail-closed startup slice

A minimal safe hardening is specifiable without proving owner death: remove the unconditional `cleanupStuckRuns()` startup call and its now-unused helper, and leave every existing `running` row unchanged. Existing admission then continues to block a same-job run while the row is `running`. This does not recover or clear the row; an interrupted run may remain blocked until a separately designed and authorized resolution exists. It introduces no status taxonomy, schema, lease, operator bypass, automatic retry, checkpoint change, or provider effect.

Age thresholds and absence from the local owner map are not substitutes for cross-process exclusion and are rejected. A durable lease/fence and recovery transaction are a broader architecture decision. The minimal slice only stops the new code path from rewriting JobRuns on startup. An older binary may still run its sweep, so mixed-version or external-writer deployments remain UNKNOWN; this source change alone cannot certify fleet-wide behavior.

The existing scheduler ownership tests cover cron and after-sync helper entrypoints but do not call `Scheduler.Start` (`backend/engine/scheduler_ownership_test.go:13-18,54-167`). A future regression must call the actual `Scheduler.Start` path with an isolated synthetic database, a JobRun-write side-effect trap, controlled jobs/channels, and bounded `Stop` cleanup. It must prove no JobRun update was attempted while separately accounting for the permitted startup sync-lease path. A helper-only test is insufficient.
